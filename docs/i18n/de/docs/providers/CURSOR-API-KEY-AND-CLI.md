Zwei Möglichkeiten, Cursor ohne IDE-Sitzung hinter OmniRoute zu betreiben:

1. **`cursor-api`-Provider** (Karte „Cursor API“, Alias `cua`): ein API-Schlüssel-
   Provider, der einen Cursor-Benutzer-API-Schlüssel (`crsr_…`, generiert unter
   `https://cursor.com/dashboard/api`) verwaltet. Jeder OmniRoute-Client kann
   Cursor-Modelle dann über `/v1/chat/completions` als `cursor-api/<model>` oder
   `cua/<model>` erreichen, einschließlich der üblichen Kontingent-, Fallback-
   und Protokollierungsebenen. Der IDE-Provider (`cursor`, OAuth/IDE-Sitzung)
   bleibt unverändert.
2. **Cursor-CLI-Passthrough**: Richten Sie die Cursor CLI (`agent`) auf OmniRoute,
   sodass jeder RPC der CLI mit einem OmniRoute-API-Schlüssel authentifiziert,
   mit den Anmeldedaten einer `cursor-api`-Verbindung an Cursor weitergeleitet
   und auf der Seite „Logs“ aufgezeichnet wird.

## Warum der Schlüssel ausgetauscht wird

`api2.cursor.sh` lehnt einen unverarbeiteten `crsr_…`-Schlüssel als Bearer-Token
ab (401). Die Cursor CLI sendet den Schlüssel zunächst per POST an
`/auth/exchange_user_api_key` und erhält ein Sitzungs-JWT, das nach einer Stunde
abläuft; das zurückgegebene `refreshToken` enthält denselben `exp`-Wert, daher
bedeutet eine Aktualisierung, dass der Schlüssel erneut ausgetauscht wird.
`open-sse/services/cursorApiKeyAuth.ts` führt diesen Austausch durch, speichert
ein Sitzungstoken pro Schlüssel zwischen, tauscht es fünf Minuten vor Ablauf
erneut aus und verwirft das zwischengespeicherte Token, wenn Cursor mit 401
antwortet. `CursorExecutor` ruft dies unmittelbar vor dem Öffnen des
Upstream-Streams für `cursor-api`-Verbindungen auf.

## Der `cursor-api`-Provider

Registrierung: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, dieselben Werte für `format`,
`baseUrl` und `models` wie bei `cursor`). Katalogkarte:
`src/shared/constants/providers/apikey/specialty-media.ts`. Executor-Zuordnung:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Dashboard: Provider → Cursor API → API-Schlüssel hinzufügen.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Danach:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Hinweise:

- Die Modellliste für `cursor-api` stammt aus der statischen Cursor-Registrierung
  (dieselbe Liste, auf die der IDE-Provider als Fallback zurückgreift); auf dem
  OmniRoute-Host muss kein `cursor-agent` installiert sein.
- `POST /api/providers/{id}/refresh-cursor` ist ausschließlich für den
  `cursor`-IDE-Provider vorgesehen; `cursor-api`-Verbindungen verfügen über
  keine IDE-Sitzung, die erneuert werden müsste.

## Cursor-CLI-Passthrough

Route: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Das Präfix `/api/cursor-cli/` ist in
`src/shared/constants/publicApiRoutes.ts` registriert, da der Handler seine
eigene Authentifizierung durchsetzt:

| Pfad                                                                                                                          | Von der CLI erwartete Authentifizierung | Was OmniRoute tut                                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                            | `Bearer <OmniRoute API key>`            | Validiert den Schlüssel, stellt ein 1 Stunde gültiges HS256-JWT aus (signiert mit `JWT_SECRET`) und gibt es zurück                                                                      |
| jeder andere Pfad (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`                     | Prüft Aussteller/Zielgruppe/Ablauf, wählt eine aktive `cursor-api`-Verbindung aus, ersetzt den Authorization-Header durch das ausgetauschte Cursor-Token und streamt die Antwort zurück |

Die CLI dekodiert `exp` aus jedem empfangenen Token. Wird ihr daher ein opakes
Token übergeben, führt sie vor nahezu jeder Anfrage einen erneuten Austausch
durch; das ausgestellte JWT verhindert dies. Bei einer 401-Antwort von
OmniRoute führt die CLI den Austausch erneut durch.

### Einrichtung

1. Erstellen Sie einen OmniRoute-API-Schlüssel (Dashboard → API-Schlüssel) und
   eine `cursor-api`-Verbindung.
2. Weisen Sie die CLI an, HTTP/1.1 für den Agenten-Stream zu verwenden. In
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Ohne diese Einstellung öffnet die CLI den Agenten-Durchlauf über HTTP/2 zu
   einem separat konfigurierten Agenten-Host, und nur die RPCs der Steuerungsebene
   laufen über den Endpunkt.

3. Führen Sie die CLI gegen OmniRoute aus:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Jeder Hop erscheint in „Logs“ mit dem Provider `cursor-api`, dem Anfragetyp
`cursor-cli` und dem Pfad `/api/cursor-cli/<rpc>` und wird dem OmniRoute-
API-Schlüssel sowie der Verbindung zugeordnet, die ihn verarbeitet hat.

### Fehlermodi

| Situation                                                  | Antwort an die CLI                                            |
| ---------------------------------------------------------- | ------------------------------------------------------------- |
| Unbekannter OmniRoute-Schlüssel und `REQUIRE_API_KEY=true` | 401 `unauthenticated` beim Austausch                          |
| `REQUIRE_API_KEY=false`                                    | anonyme Sitzung (entspricht dem Verhalten von `/v1/*`)        |
| Abgelaufenes / fremdes / manipuliertes Sitzungs-JWT        | 401, die CLI führt den Austausch erneut durch                 |
| OmniRoute-API-Schlüssel nach dem Austausch widerrufen      | 401 beim nächsten RPC                                         |
| Keine aktive `cursor-api`-Verbindung                       | 503 `unavailable`                                             |
| Cursor lehnt den Schlüssel der Verbindung ab               | 401 `unauthenticated`, zwischengespeicherte Sitzung verworfen |
| Upstream nicht erreichbar                                  | 502 `unavailable` (bereinigte Meldung)                        |
| `JWT_SECRET` nicht gesetzt                                 | 503 beim Austausch                                            |
