> **مخاطبان:** مهندسانی که سرویسهای تعبیهشده (9Router، CLIProxyAPI، Mux، Bifrost) را اضافه، نگهداری یا اشکالزدایی میکنند.

سرویسهای تعبیهشده ابزارهای فرایند جانبیِ نصبشده روی سیستم محلی هستند که OmniRoute آنها را نصب و نظارت میکند و
بهعنوان مقصدهای مسیریابی سطحاول ارائه میدهد. برخلاف ارائهدهندگان خارجی (که از طریق اینترنت
و با استفاده از کلیدهای API به آنها دسترسی میشود)، سرویسهای تعبیهشده روی همان دستگاه OmniRoute اجرا میشوند و از طریق loopback ارتباط برقرار میکنند.

## 1. نمای کلی

### چرا سرویسهای تعبیهشده؟

پنج سرویس تعبیه شدهاند:

| سرویس           | بستهٔ npm                              | پورت پیشفرض | هدف                                                                                                                                                                                               |
| --------------- | -------------------------------------- | :---------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                              |    20130    | مسیریاب هوش مصنوعی که OmniRoute میتواند از آن بهعنوان ارائهدهندهٔ فرعی استفاده کند. مدلها بهشکل `9router/{sub}/{model}` ارائه میشوند                                                              |
| **CLIProxyAPI** | فایل اجرایی انتشار GitHub (`cliproxy`) |    8317     | آداپتور پراکسی محلی برای جریانهای احراز هویت Anthropic CLI. هنگامی که توکنهای OAuth منقضی میشوند، مسیریابی جایگزین را فراهم میکند                                                                 |
| **Mux**         | `mux` (`mux server` بدون رابط گرافیکی) |    8322     | دیمن محلی هماهنگسازی عاملها (coder/mux). فقط چرخهٔ حیات آن مدیریت میشود — مقصد مسیریابی نیست (هیچ پراکسی LLM انجام نمیدهد).                                                                       |
| **Bifrost**     | `@maximhq/bifrost`                     |    8080     | بکاند رلهٔ دروازهٔ هوش مصنوعی Go. هنگام اجرا، بهطور خودکار توسط مسیر رله (`/v1/relay/`) انتخاب میشود                                                                                              |
| **Dario**       | `@askalf/dario`                        |    3456     | پراکسی اشتراک Claude — جایگزین/پشتیبان CLIProxyAPI برای ترافیک با ساختار Claude-Code؛ کلید تزریقشده به `DARIO_ADMIN_TOKEN` تبدیل میشود و دسترسی به صفحهٔ کنترل OAuth در `/admin/*` را محدود میکند |

هر پنج سرویس از یک مدل نظارتی مشترک پیروی میکنند:

- OmniRoute آنها را در `DATA_DIR/services/{name}/` نصب میکند (جدا از `package.json` خود OmniRoute)
- OmniRoute آنها را بهعنوان فرایندهای فرزند اجرا و پایش میکند
- OmniRoute یک کلید API موقت را به محیط فرایند فرزند تزریق میکند و آن را بدون توقف سرویس میچرخاند (در موارد قابلاعمال)
- همهٔ مسیرهای مدیریتی (`/api/services/*`) **LOCAL_ONLY** هستند — فقط از loopback قابلدسترسیاند (قانون قطعی شمارهٔ ۱۷)

### تصمیمهای کلیدی (برگرفته از طرح طراحی)

| تصمیم                                      | مقدار                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| دسترسی داشبورد به رابط کاربری بومی 9Router | پراکسی معکوس در `/dashboard/providers/services/9router/embed/*`                                              |
| سازوکار نصب                                | `npm install {package}` از طریق `execFile` (بدون درونیابی پوسته)                                             |
| حالت استفاده                               | ارائهدهنده بهشکل `9router/{sub}/{model}` در موتور مسیریابی ثبت میشود                                         |
| مدیریت کلید API                            | OmniRoute آن را تولید میکند، در حالت ذخیرهشده رمزنگاری میکند (AES-256-GCM) و از طریق متغیر محیطی تزریق میکند |
| محل داشبورد                                | `/dashboard/providers/services` (سه زبانه)                                                                   |
| شروع خودکار                                | کلید تغییر وضعیت برای هر سرویس، بهطور پیشفرض خاموش                                                           |

## 3. ماشین حالت چرخهٔ حیات

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
            کاوش سلامت موفق است     │         خرابی / SIGTERM    │
                               ┌────▼─────┐  (خروج ظرف 5 ثانیه) │
                               │ running  │──── خرابی ──────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

حالتها در جدول `version_manager` پایگاه داده (ستون `status`) ذخیره میشوند و در
حالت درونحافظهای `ServiceSupervisor` نیز بازتاب مییابند. برای یک فرایند در حال
اجرا، حالت درونحافظهای مرجع نهایی است؛ حالت پایگاه داده، جایگزین پایدار هنگام راهاندازی سیستم است.

### گذارهای حالت

| از              | رویداد                                        | به                     |
| --------------- | --------------------------------------------- | ---------------------- |
| `not_installed` | `install()` با موفقیت انجام میشود             | `stopped`              |
| `stopped`       | `start()` فراخوانی میشود                      | `starting`             |
| `starting`      | کاوش سلامت مقدار 200 را برمیگرداند            | `running`              |
| `starting`      | فرایند پیش از سالمشدن خارج میشود              | `error`                |
| `running`       | `stop()` فراخوانی میشود                       | `stopping` → `stopped` |
| `running`       | فرایند بهطور غیرمنتظره خارج میشود (< 5 ثانیه) | `error` (خرابی سریع)   |
| `running`       | فرایند بهطور غیرمنتظره خارج میشود (> 5 ثانیه) | `error`                |
| `error`         | `start()` فراخوانی میشود                      | `starting`             |
| هر حالت         | `stop()` هنگام `stopping`                     | بدون عملیات            |

### قفل عملیات

`ServiceSupervisor` عملیات چرخهٔ حیات را از طریق یک قفل عملیات ناهمگام
(`withLock()`) بهصورت ترتیبی اجرا میکند. فراخوانیهای همزمان `start()` روی یک سرپرست یکسان،
دقیقاً به ایجاد یک فرایند منجر میشوند؛ فراخوان دوم منتظر میماند و وضعیت موجود را برمیگرداند. این کار
از شرایط رقابتی جلوگیری میکند؛ برای مثال، زمانی که شروع خودکار و یک دکمهٔ رابط کاربری همزمان فعال میشوند.

## 4. مرجع API

تمام مسیرهای زیرمجموعهٔ `/api/services/` **LOCAL_ONLY** هستند (فقط loopback، قانون قطعی شمارهٔ 17).
درخواستهای غیرـloopback، صرفنظر از توکن احراز هویت، پاسخ `403 LOCAL_ONLY` دریافت میکنند.

### 4.1 نقاط پایانی 9Router (11 مسیر)

#### `POST /api/services/9router/install`

9Router را از npm نصب میکند. مسیر `DATA_DIR/services/9router/` را همراه با
`package.json` و `node_modules/` اختصاصی آن ایجاد میکند. با وابستگیهای خود OmniRoute تداخلی ندارد.

**بدنهٔ درخواست** (همه اختیاری):


### 4.6 پراکسی معکوس (تعبیه داشبورد 9Router)

داشبورد، رابط وب 9Router را از طریق یک پراکسی معکوس داخلی درون iframe
تعبیه میکند:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

این پراکسی:

- درخواست را به `http://127.0.0.1:{port}/{path}` هدایت میکند (فقط loopback)
- هدرهای ورودی `cookie` و `authorization` را حذف میکند (بدون نشت نشست OmniRoute)
- برای احراز هویت 9Router، `Authorization: Bearer {apiKey}` را تزریق میکند
- موارد `set-cookie`، `content-security-policy`، `x-frame-options` و `cross-origin-*` را از پاسخ حذف میکند
- پاسخهای HTML را برای تزریق `<base href>` و نرمالسازی مسیرهای مطلق بازنویسی میکند (`/foo` ← `/dashboard/.../embed/foo`)

ارتقاهای WebSocket برای داشبورد تعبیهشده توسط یک سرور همراه روی
پورتی اختصاصی مدیریت میشوند (به `src/lib/services/embedWsProxy.ts` مراجعه کنید).

**امنیت:** مسیرهای پراکسی تعبیهشده زیرمجموعه `LOCAL_ONLY_API_PREFIXES`
طبقهبندی شدهاند و فقط از طریق loopback قابل دسترسی هستند. مهاجمی که از طریق یک
تونل Cloudflare/Ngrok به JWT دست یابد، نمیتواند به سرویسهای تعبیهشده پراکسی بزند.

## 5. امنیت

### اعمال LOCAL_ONLY (قانون سختگیرانه #17)

تمام مسیرهای زیرمجموعه `/api/services/` و `/dashboard/providers/services/*/embed/` در
`src/server/authz/routeGuard.ts` بهعنوان LOCAL_ONLY طبقهبندی شدهاند. بررسی loopback
بدون هیچ شرطی و پیش از هر شاخه احراز هویت اجرا میشود:

```
درخواست وارد میشود
  → isLocalOnlyPath(path)?
      → غیر-loopback → 403 LOCAL_ONLY (همیشه، پیش از بررسی احراز هویت)
      → loopback     → ادامه به احراز هویت عادی
```

این کار مانع میشود که یک JWT افشاشده (برای مثال، از طریق یک تونل) بتواند `npm install`
یا ایجاد فرایند را فعال کند. برای مشاهده ماتریس کامل سطوح، به
`docs/security/ROUTE_GUARD_TIERS.md` مراجعه کنید.

### تزریق کلید API

9Router و Mux برای endpointهای HTTP خود به یک کلید API یا bearer token نیاز دارند.
OmniRoute:

1. با استفاده از `crypto.randomBytes(32).toString("base64url")` و یک پیشوند
   مختص سرویس (`nr_` برای 9Router و `mx_` برای Mux) کلیدی تولید میکند.
2. آن را در حالت ذخیرهشده با AES-256-GCM رمزنگاری میکند (همان رمزی که برای اطلاعات احراز هویت ارائهدهنده استفاده میشود).
3. هنگام ایجاد فرایند، آن را رمزگشایی کرده و بهصورت یک متغیر محیطی تزریق میکند —
   `NINEROUTER_API_KEY` برای 9Router و `MUX_SERVER_AUTH_TOKEN` برای Mux (هرگز بهصورت
   یک پرچم CLI ارسال نمیشود، بنابراین توکن هیچگاه در فهرستهای `ps`/فرایند ظاهر نمیشود).
4. کلید متن ساده را هرگز در هیچ پاسخ HTTP بازنمیگرداند.

CLIProxyAPI یک کلید اختصاصی data-plane دریافت میکند که هنگام ایجاد فرایند تزریق میشود
(`needsApiKey: true` — برای همگامسازی مدل با adapter استفاده میشود).

### دفاع در برابر SSRF

پروکسی معکوس HTTP (`/dashboard/.../embed/[...path]`) بهصورت hardcoded تنظیم شده است تا
فقط درخواستها را به `http://127.0.0.1:{port}` هدایت کند. این پروکسی هرگز تغییرمسیرها
به مقصدهای غیر-loopback را دنبال نمیکند. از کتابخانه `ssrf-req-filter` برای رد کردن
هر URL بالادستی که به آدرسی خارج از محدوده loopback resolve شود، استفاده میشود.

### ایمنی shell (قانون سختگیرانه #13)

`npm install` از طریق `execFile('npm', ['install', pkg, '--prefix', dir])` فراخوانی میشود —
بدون template literal، بدون shell و بدون درونیابی مسیرهای خارجی در رشته فرمان.
مقادیر زمان اجرا (پورتها و کلیدهای API) از طریق شیء `env` فرایند فرزند ارسال میشوند.

### پاکسازی خطاها (قانون سختگیرانه #12)

تمام پاسخهای خطای `/api/services/*` از `buildErrorBody()` یا
`sanitizeErrorMessage()` عبور میکنند. مقادیر خام `err.stack` و `err.message` هرگز
عیناً به فراخواننده بازگردانده نمیشوند.

## 6. افزودن یک سرویس تعبیهشده جدید

این 8 مرحله را دنبال کنید. پیادهسازیهای موجود در `src/lib/services/installers/`
و `src/app/api/services/` را بهعنوان مرجع معیار مطالعه کنید.

### مرحله 1 — ایجاد نصبکننده

فایل `src/lib/services/installers/{name}.ts` را با الگوبرداری از `ninerouter.ts` ایجاد کنید:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // یک پورت آزاد انتخاب کنید

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

از `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` موجود در `installers/utils.ts`
استفاده کنید — هرگز از `execSync` یا درونیابی shell استفاده نکنید.

### مرحله 2 — ثبت در bootstrap

یک `ServiceEntry` به آرایه `SERVICES` در `src/lib/services/bootstrap.ts` اضافه کنید:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // اگر به کلید API نیازی نیست، false
}
```

`buildSpawnArgsFactory()` را برای پشتیبانی از `cfg.tool === "myservice"` گسترش دهید.

#### قرارداد provider-plugin قابل اتصال (فاز 1، #7333)

`src/lib/services/providerPlugins/` یک قرارداد `ServiceProviderPlugin` معرفی میکند که
فیلدهای `ServiceEntry` مربوط به `bootstrap.ts` یک backend و فیلدهای manifest-template
مربوط به `serviceBackends.ts` را در یک شیء بستهبندی میکند؛ بهجای اینکه ساختار همان
backend بهصورت جداگانه در دو فایل نامرتبط بیان شود. تا زمان نگارش این متن،
**فقط `9router` مهاجرت داده شده است** — `bootstrap.ts` ورودی `SERVICES[]` آن را از
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`)
استخراج میکند و اگر plugin وجود نداشته باشد، هنگام راهاندازی خطا ایجاد میکند.
`cliproxy`، `mux` و `bifrost` بدون تغییر همچنان از literalهای inline از پیش موجود
`SERVICES[]` استفاده میکنند.

`open-sse/config/providerPluginManifest.ts` همچنین یک helper افزایشی با نام
`createServiceBackendManifestEntry(pluginId, template)` دریافت کرده است که یک
`ProviderPluginManifestEntry` خوشساخت را از یک ورودی `SERVICE_BACKEND_MANIFEST_TEMPLATE`
میسازد — این helper هنوز به هیچ مسیر درخواست فعالی متصل نشده است (نه
`generateProviderPluginManifestFromRegistry()` و نه `/v1/providers/[provider]/models`)؛
پس از اثبات قرارداد برای دومین backend، این کار در ادامه انجام خواهد شد.

موارد زیر به PRهای بعدی موکول شدهاند و تحت issue شماره #7333 پیگیری میشوند:
مهاجرت `cliproxyapi` از طریق همان registry، تعمیم `mux`/`bifrost` در union نوع
`ServiceBackendPluginId`، ادغام حالتهای ویژه مسیریابی executor
(`open-sse/executors/index.ts`، `open-sse/handlers/chatCore/executorProxy.ts`) در قرارداد
plugin، و اتصال `createServiceBackendManifestEntry()` به یک مسیر کد فعال manifest/models.

## ۷. عیبیابی

### سرویس راهاندازی نمیشود

**نشانهها:** دکمه شروع کد 503 را برمیگرداند و وضعیت روی `"error"` یا `"starting"` باقی میماند.

**فهرست بررسی:**

1. مسیر `GET /api/services/{name}/logs` (یا پنل Logs در داشبورد) را بررسی کنید. بهدنبال
   خطوطی مانند `Error: ENOENT`، `address already in use` یا `Cannot find module` بگردید.
2. مطمئن شوید `npm` در PATH قرار دارد: دستور `which npm` را از همان حساب کاربری اجرا کنید که OmniRoute را اجرا میکند.
3. مطمئن شوید سرویس نصب شده است: در پاسخ `GET /api/services/{name}/status`، مقدار
   `installedVersion` را بررسی کنید. اگر `null` است، ابتدا نصب را اجرا کنید.
4. بررسی کنید که `DATA_DIR/services/{name}/node_modules/` وجود داشته باشد و خالی نباشد.
5. برای مشاهده دلیل پالایششده خروج، فیلد `lastError` را در پاسخ وضعیت بررسی کنید.

---

### راهاندازی سرد کند است (بیش از ۱۰ ثانیه برای رسیدن به `running`)

**نشانهها:** وضعیت برای مدت زیادی روی `"starting"` باقی میماند و سپس به `"running"` یا `"error"` تغییر میکند.

**توضیح:** راهاندازی سرد 9Router شامل وارد کردن درختهای وابستگی بزرگ (ماژولهای DNS،
تونل و MITM) است. بازه پیشفرض بررسی سلامت ۲ ثانیه با ۳ تلاش است؛ پس از آن
ناظر وقوع مهلت زمانی را اعلام میکند (اما نظرسنجی را ادامه میدهد).

**راهحل:** مقدار `healthIntervalMs` و مهلت زمانی `waitForHealthy`
(`healthIntervalMs * 3`) در `bootstrap.ts` قابل پیکربندی هستند. برای سرویسهایی با زمان
راهاندازی طولانیتر، `healthIntervalMs` را به 5000 و `stopTimeoutMs` را به 30 000 افزایش دهید.

---

### تداخل پورت (`EADDRINUSE`)

**نشانهها:** گزارشها پیام `address already in use :::20130` را نشان میدهند.

**دلایل:**

- فرایند دیگری در حال استفاده از پورت 20130 است.
- فرایند قبلی 9Router بهطور کامل متوقف نشده است (PID زامبی).

**راهحل:**

1. پورت پیشفرض را از طریق متغیر محیطی `NINEROUTER_PORT` در `.env` تغییر دهید.
2. فرایند متداخل را پیدا کرده و متوقف کنید: `lsof -ti :20130 | xargs kill -9`.
3. پورت هر سرویس از طریق فیلد `port` در `bootstrap.ts` قابل پیکربندی است.

**توجه:** 9Router بهطور پیشفرض از پورت 20130 استفاده میکند تا مشخصاً با
پورت پیشفرض 20128 در OmniRoute تداخل نداشته باشد.

---

### رد شدن مجوز (EACCES) هنگام نصب

**نشانهها:** نصب کد 500 را برمیگرداند و گزارشها `EACCES` یا `permission denied` را نشان میدهند.

**دلایل:**

- `DATA_DIR` یا دایرکتوری والد آن توسط فرایند OmniRoute قابل نوشتن نیست.
- اجرا در Docker بدون دسترسی ریشه و بدون دسترسی نوشتن در ولوم نگاشتشده.

**راهحل:**

1. `DATA_DIR` را بررسی کنید (پیشفرض: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. مطمئن شوید کاربرِ فرایند OmniRoute مالک دایرکتوری است: `chown -R $USER ~/.omniroute/`
3. در Docker، مطمئن شوید اتصال ولوم مجوزهای صحیح را برای کاربر کانتینر دارد.

---

### بهروزرسانی ناموفق است (اتمام مهلت `npm install` یا خطای شبکه)

**نشانهها:** بهروزرسانی کد 500 را همراه با `InstallError` برمیگرداند و گزارشها اتمام مهلت شبکه را نشان میدهند.

**فهرست بررسی:**

1. در دسترس بودن رجیستری npm را تأیید کنید: `npm ping`.
2. وجود پراکسی سازمانی را بررسی کنید: `npm config get proxy`، `npm config get https-proxy`.
3. نصب را بهصورت دستی امتحان کنید: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. اگر پشت یک شبکه کاملاً ایزوله هستید، tarball را از قبل دانلود کنید و از `npm install /path/to/tarball.tgz` استفاده کنید.

---

### سرویس بلافاصله پس از شروع، وضعیت `"error"` را نشان میدهد (خرابی سریع)

**نشانهها:** وضعیت در کمتر از ۵ ثانیه از `"starting"` به `"error"` تغییر میکند.
`lastError` مقدار `"Fast crash (exited with code 1)"` را نشان میدهد.

**فهرست بررسی:**

1. انتهای کامل گزارش را بخوانید: `GET /api/services/{name}/logs?tail=500`.
2. دلیل رایج: متغیرهای محیطی مورد انتظار سرویس وجود ندارند.
3. برای 9Router: بررسی کنید که `NINEROUTER_DISABLE_MITM=true` و
   `NINEROUTER_DISABLE_TUNNEL=true` در محیط ارسالشده هنگام ایجاد فرایند قرار داشته باشند (به
   `resolveSpawnArgs` در `installers/ninerouter.ts` مراجعه کنید).

## 8. پرسشهای متداول

**س: آیا میتوانم endpointهای سرویسهای تعبیهشده را در دسترس کلاینتهای غیر-loopback قرار دهم؟**

خیر. سطح LOCAL_ONLY عامدانه در نظر گرفته شده است (قانون قطعی شمارهٔ 17). مسیرهایی که میتوانند
`npm install` را اجرا کنند یا پردازشهای `node` را ایجاد کنند، نباید از طریق ترافیک
غیر-loopback قابل دسترسی باشند؛ زیرا در غیر این صورت، افشای JWT از طریق یک تونل
(Cloudflare، Ngrok، Tailscale) امکان ایجاد پردازشهای دلخواه را فراهم میکند. هیچ استثنایی برای
نادیدهگرفتن این محدودیت در مورد `/api/services/` وجود ندارد — برخلاف `/api/mcp/`، این مسیر
در فهرست عبور از محدودیت manage-scope قرار نگرفته است. به `docs/security/ROUTE_GUARD_TIERS.md` مراجعه کنید.

---

**س: آیا 9Router و CLIProxyAPI در استقرارهای production/cloud در دسترس خواهند بود؟**

بله. هر دو سرویس از همان مدل local-first خود OmniRoute پیروی میکنند. آنها
روی همان ماشین اجرا میشوند و از طریق loopback ارتباط برقرار میکنند. منظور از «Production» در اینجا VPS
یا سرور محلیای است که OmniRoute روی آن مستقر شده است، نه یک ارائهدهندهٔ cloud راهدور.

---

**س: چگونه supervisor را اشکالزدایی کنم؟**

1. جریان لاگ SSE را دنبال کنید: `curl -N http://localhost:20128/api/services/9router/logs`.
2. لاگهای ساختیافته را در خروجی pino متعلق به OmniRoute که بر اساس فضای نام
   `service:supervisor` فیلتر شدهاند، بررسی کنید.
3. ردیف DB را بررسی کنید: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. برای مشاهدهٔ وضعیت زندهٔ فعلی، PID، سلامت،
   و `lastError` در یک فراخوانی، از `GET /api/services/9router/status` استفاده کنید.

---

**س: supervisor مقدار `health: "degraded"` یا `health: "unknown"` را نشان میدهد، اما state برابر با `"running"` است. آیا این مشکلساز است؟**

`"degraded"` یعنی پروب سلامت پاسخی غیر از 200 دریافت کرده است. `"unknown"` یعنی هنوز هیچ
پروبی تکمیل نشده است (شرایط رقابتی با نخستین poll). هر دو حالت هنگام راهاندازی موقتی هستند.
اگر سلامت پس از `"running"` شدن، بیش از `healthIntervalMs * 3` میلیثانیه
در وضعیت `"degraded"` باقی بماند، سرویس تعبیهشده در حال اجرا است، اما API مبتنی بر HTTP آن پاسخ نمیدهد. بررسی کنید
که آیا پورت در پاسخ وضعیت صحیح است و آیا سرویس واقعاً
روی آن پورت در حال گوشدادن است یا خیر.

---

**س: آیا میتوانم کلید API مربوط به 9Router را بدون راهاندازی مجدد کامل تغییر دهم؟**

خیر. کلید API هنگام ایجاد پردازش از طریق یک متغیر محیطی به 9Router ارسال میشود.
متغیرهای محیطی را نمیتوان در یک پردازش در حال اجرا تغییر داد. `POST .../rotate-key`
برای اعمال کلید جدید، سرویس را بهطور خودکار متوقف و دوباره راهاندازی میکند. چرخش کلید
در مدت `stopTimeoutMs` سرویس (مقدار پیشفرض 15 ثانیه) بهعلاوهٔ زمان راهاندازی آن
اعمال میشود.

---

**س: محدودیت ring buffer چقدر است و وقتی پر شود چه اتفاقی میافتد؟**

هر سرویس یک ring buffer اختصاصی 5 مگابایتی دارد. وقتی بافر پر شود، قدیمیترین
خطوط لاگ حذف میشوند تا برای خطوط جدید جا باز شود. رویداد `snapshot` در SSE،
جدیدترین خطوط را تا سقف محدودیت `tail` بازمیگرداند. لاگها روی دیسک ماندگار نمیشوند، مگر اینکه
`logsBufferPath` در ردیف DB تنظیم شده باشد.
